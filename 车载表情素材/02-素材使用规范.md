# 车载表情素材使用规范

版本：v1.3。面向素材整理、EAF 转换、MEPACK 打包和喵伴 2.0 固件开发。

## 1. 目录职责

- 编号表情包目录是可交付资源的唯一入口。`gif/` 用于电脑预览，`eaf/` 是固件候选，两个总览文件只用于人工审阅。
- [`源素材/`](源素材/) 仅保存分镜、提示词、原视频、提取文件和历史转换说明；不要把其中的 MP4、ZIP、MJPEG、BIN 或设计 PNG 打入 assets 分区。
- 固件引用固定版本目录，不使用“最新”“final”“最终版”等浮动路径，也不递归收集整个素材库。
- `设备资源包/` 只保存由已批准素材母版生成的 `.mepack` 和发布校验文件；设备包不得反向替代或覆盖素材母版。

## 2. 预览先行与用户审批

静态设计图转动态表情采用“两阶段交付”，预览未获用户明确确认前，不生成正式资源文件：

1. 先核对静态图中的状态、中文名称、方向、角色结构和颜色语义，按 [`01-基础设计规范.md`](01-基础设计规范.md) 制作动态方案。允许使用临时中间帧，但临时帧不作为正式资源交付。
2. 第一阶段只输出 `全部表情预览.gif` 和 `全部静态表情预览.png`。动态总览用于检查每个状态的完整动作、节奏和色彩延伸；静态总览从同一批动态方案中选取代表帧，用于检查造型、状态区分和整体一致性。
3. 两个总览必须覆盖计划制作的全部状态，使用相同顺序、相同中文标签和一致的缩放比例。总览中的标签用于审阅，不烧入单个 360×360 动画帧。
4. 将两份总览交给用户预览。用户提出修改时，先修改动态方案并重新生成两份总览；未收到“满意”“通过”或等价的明确确认，不得把沉默、未回复或局部意见视为批准。
5. 用户明确确认后，第二阶段才生成逐状态 GIF、EAF、`manifest.json`、单包 README 及其他对应资源。设备包打包和固件接入是后续独立阶段，仍以用户本次授权为准。
6. 正式资源生成后，必须再从最终逐状态 GIF 重建两份总览并与已确认版本核对。若转换或优化导致动作、颜色、裁切、节奏或状态覆盖发生可见变化，必须重新提交预览确认。

审批前不得将临时动画复制到 `car_packs/`、写入固件资源清单、构建 assets 镜像或宣称表情包已经交付。审批只确认视觉方向，不替代 EAF 结构、容量和实机播放验证。

## 3. 固件接入流程

1. 选择一个明确的 `NNN-名称-vN` 目录，读取该包 README，确认状态覆盖、来源、授权和待验证项。
2. 根据当前功能状态建立显式白名单，只复制所需 `eaf/car_<state>.eaf` 到板级 `car_packs/<pack_id>/`；不要把三套资源无条件全部打包。
3. 将运行时资源登记为 `car_<pack_id>_<state>`，车辆事件只依赖 `<state>`，视觉样式只依赖 `<pack_id>`。切包不能修改运动检测逻辑。
4. 核对 `eaf/manifest.json` 中的尺寸、帧数、逐帧时长、大小和 SHA-256；复制后再次计算校验值，不能只看同名文件存在。
5. 运行资源准备与镜像校验，再执行 V2.0 正式构建。最终以生成的 `expression_assets.bin` 和实际分区表判定容量，不以源文件合计大小代替。
6. 在实机测试颜色、方向、圆屏裁切、帧率、解码内存、切包恢复和长时间播放。没有实机证据时保留“待实机验证”。

当前相关入口：

- `main/boards/CyberVoc-Board-V2_0/car_packs/`：本次固件实际采用的 EAF 白名单。
- `scripts/prepare_v2_assets.py`：在 build 目录抽帧并生成 V2.0 资源配置，不修改本素材库原件。
- `scripts/verify_v2_images.py`：检查最终应用、assets、model、分区位置和 EAF 结构。

## 4. MEPACK 设备包流程

正式 GIF/EAF 与母版 manifest 已通过检查后，构建选择器和 TF 卡统一使用 [`04-MEPACK资源包规范.md`](04-MEPACK资源包规范.md) 定义的 `NNN-<pack_id>-vN.mepack`。母版不直接复制到 TF 卡，`.mepack` 也不放回编号母版目录。

1. 从一个明确版本的母版调用 `工具/生成mepack.py pack`；打包器从目录名和 README 获取编号、展示名、版本和 `pack_id`。
2. 打包前再次核对 GIF/EAF 文件集合、必备状态、尺寸、EAF 结构及母版 manifest 中的帧数、大小和 SHA-256。
3. 输出只包含设备清单、索引和原始 EAF payload，同时生成整包 `.sha256`；不得把预览、README、源文件或脚本装入容器。
4. 对输出执行 `工具/生成mepack.py verify` 完整回读。同一母版和参数重复打包的 SHA-256 必须一致。
5. 主机校验通过只说明容器完整；固件加载、TF 菜单、PSRAM 峰值、拔卡恢复和长时间播放未验证时继续标为“待设备验证”。

构建时选择表情包应选择明确的 `.mepack` 或由相同工具链生成的明确 profile，并把包身份与 SHA-256 写入发布清单。未选中的包不得进入最终镜像。

## 5. 当前 EAF 基线

现有候选 EAF 为 360×360、8-bit 索引色 BGRA 调色板、RLE 编码、每帧 12 个 30 行分块。后续若转换格式发生变化，必须同时更新转换工具、播放器兼容性说明、manifest 和实机验证记录；不能只替换扩展名。

`gif/` 不是固件资源来源。GIF 的颜色量化、循环设置和帧时长用于预览，不足以证明 EAF 播放结果一致。

## 6. 状态与回退

当前固件最小状态集及中文含义：

| 逻辑文件名 | 中文含义 | 建议策略 |
|---|---|---|
| `car_cruise` | 巡航 | 中性、低频循环；全包必备 |
| `car_idle_01`～`car_idle_03` | 待机动画组 | 默认至少三种；完整播放后随机选择 |
| `car_wait` | 等候/校准 | 安静循环；校准期间使用 |
| `car_accelerate` | 加速 | 瞬态、冷却后再触发 |
| `car_decelerate` | 减速 | 瞬态，不等同急刹 |
| `car_hard_brake` | 急刹 | 高优先级单次，有驻留上限 |
| `car_bump` | 颠簸 | 短时单次，限制连续触发 |
| `car_turn_left` | 左转 | 按可信方向输入进入/保持 |
| `car_turn_right` | 右转 | 按可信方向输入进入/保持 |
| `car_signal_lost` | 信号中断 | 数据不可用时优先显示 |

缺失资源按以下顺序回退：同包指定状态 → 同包 `car_cruise` → 固件内置中性表情。回退必须在资源映射或单包 README 中明确，日志不得把回退素材报告成真实专用动画。当前 TITA 包缺少加速、减速和急刹专用动画，三项统一回退到 TITA 巡航。

待机动画组与 `car_cruise`、`car_wait`、`car_sleep` 是不同语义。新建或升级包必须至少提供 `car_idle_01`～`car_idle_03`，且 GIF/EAF 均存在并通过清单校验；已有 001～003 的 v1 包作为规则生效前的历史版本保留，不得通过复制巡航或其他状态来伪造合规，下一次实质素材升级时补齐并递增为 v2。

扩展状态 `wake`、`move_off`、`turn_end`、`reverse`、`arrive`、`sleep`、`night` 只有在固件具备对应生命周期或可信输入时接入。倒车不能由普通 IMU 加速度推断。

## 7. 播放与生命周期

- 车载表情走纯显示路径，不调用可能联动底座动作的通用情绪接口。
- Listening、Speaking、系统告警和通知优先于普通车载表情；抢占结束后根据当前实时状态恢复，不恢复旧快照。
- 车载循环不持续占用单一临时动画槽；相同状态不重复重启动画。
- 进入普通待机时，从已成功加载且校验通过的 `car_idle_NN` 池中随机选择；每个动画完整播放一次后再选择下一项。池内至少有 2 项可用时，本轮抽选排除上一项，避免连续重复。
- 待机池默认等概率；如需权重，必须使用稳定配置并记录在单包 README 或清单中。随机数异常不得造成越界、空资源引用或逐帧重选。
- 个别待机资源缺失或损坏时，只从其余有效项中选择并记录降级；全部不可用时回退到同包 `car_cruise`，再失败则使用固件内置中性表情。
- 转向、制动、颠簸、语音和系统告警等高优先级状态可以中断待机；结束后根据最新实时状态重新进入待机池，不续播被打断的旧帧快照。
- 切包时保留当前车辆业务状态，确认新资源完整加载后再释放旧解码器；失败继续使用旧包。
- 表情全屏显示时，电量、时钟等叠加层是否隐藏由显示层统一处理，不能把这些 UI 烧进动画帧。
- TF 卡加载不能把文件路径直接当作 EAF 内存指针。扫描只读取包头、清单和索引；切换时将目标动画读入 PSRAM，校验成功后再替换当前资源所有者。
- 文件读取、整包哈希和 TF 扫描不得在显示、IMU 或触摸高频回调中执行。TF 卡丢失或读取失败时保留仍有效缓存，并按清单回退到同包巡航，再回退到 Flash 内置中性表情。

## 8. 容量与发布检查

- 当前 V2.0 `assets` 分区为 5500 KiB；每次变更都以实际镜像重新测量并保留打包余量。
- 优先减少低价值状态、帧数或时长，再考虑分区变化。不得为加入表情包擅自修改 bootloader、OTA 或安全配置。
- 发布前记录：选用包和版本、状态白名单、源/目标 SHA-256、转换参数、最终镜像字节数、构建命令和实机结果。
- 更新素材通常需要同步更新 assets 分区；只更新应用 OTA 不会自动获得新 EAF。
- TF 卡包不占 assets 分区，但需要按“当前动画 + 巡航缓存 + 解码工作区”核对 PSRAM 峰值；不能仅以 `.mepack` 总大小判断运行内存。

## 9. 最低验收清单

- [ ] 包目录和文件名通过 [`03-命名规则.md`](03-命名规则.md) 检查。
- [ ] 已先提交动态、静态两份总览并取得用户明确确认；确认前没有生成或接入正式逐状态资源。
- [ ] 从最终逐状态 GIF 重建的总览与获批预览一致；存在可见差异时已重新确认。
- [ ] GIF 与 EAF 状态一一对应，manifest 无缺失或多余项。
- [ ] 新建或升级包包含至少 3 个连续编号且内容不同的待机动画；随机播放、避免立即重复和全失效回退均已验证。
- [ ] 预览生成脚本通过，动态/静态总览均为中文标签。
- [ ] EAF 结构、校验和、RLE 回读和最终 assets 镜像检查通过。
- [ ] 需要构建/TF 交付时，`.mepack` 完整回读、确定性复打包和整包 SHA-256 通过；包内不含非设备资源。
- [ ] 资源缺失、损坏和切包失败均能回退，不崩溃、不静默成功。
- [ ] 360×360 实机完成颜色、方向、裁切、帧率、内存和长时间播放验证。
